# AiKi on-chain mandates

ERC-7710-style delegation with caveat enforcers for bounded agent actions.

AiKi is a marketplace for humans and agents to get work done together. These
contracts support jobs that need permission to act on an account. They restrict
the calls an agent can make under a signed delegation. A job's price and payment
agreement are separate from that action authority. See
[Product definition](../docs/PRODUCT.md) and
[Marketplace API v2](../docs/03-marketplace-api-v2.md).

The API pins a deployed suite on BNB testnet, chain 97, in
[`apps/api/src/config/enforcers.ts`](../apps/api/src/config/enforcers.ts), which
records its 29 August 2026 deployment, addresses and enforcer code hashes. This
is not a mainnet deployment claim. Startup assertions check the configured RPC,
bytecode and registry mappings. **The suite is unaudited.** A deployed contract,
passing test or internal review is not an independent security audit.

## Current integration boundaries

- The API derives enforcement tiers from caveat compilation against its configured deployment. A caller-supplied `T0` label is not sufficient.
- An unsigned authorization remains an AiKi-side record. Chain enforcement requires the accepted signed delegation, the correct account authority and supported caveats.
- Target, selector, asset, per-action amount, lifetime amount and expiry have enforcers. Conditions and approval workflow are handled separately by the application; this suite has no rolling monthly-cap enforcer.
- `POST /v1/authorizations/:id/revoke` currently revokes AiKi's stored authorization. It does not broadcast a manager revocation transaction. The MCP `revoke_mandate` tool calls that route.
- `disableDelegation`, `disableDelegationWithSig` and `bumpEpoch` exist in the contracts. On-chain revocation requires a transaction and takes effect on inclusion. Stopping a watch or updating an API record does not invalidate a signed delegation already held by an agent.
- Hiring another worker does not redelegate this account's authority. This manager rejects redelegation; agent-to-agent or agent-to-human commerce needs its own authorized job and payment path.

## Policy parity

The off-chain evaluator, `apps/api/src/authority/policy.ts`, defines the API's
action checks. The enforcers mirror the representable constraints and their
boundaries; the explicit differences below remain part of the integration
contract. Application approval rules and purchase policy have separate checks.

That match is not asserted, it is **tested**. `test/vectors/policy-vectors.json` is generated by
`tools/gen-vectors.mjs`, which imports the real `evaluatePolicy` and records its verdict for
the policy cases. `test/Parity.t.sol` replays them against enforcers deployed in the test harness and asserts the
chain returns the identical `allow`, the identical `rule`, and the identical `reason` string.

```
npx tsx tools/gen-vectors.mjs         # regenerate the policy corpus from the real evaluatePolicy
npx tsx tools/gen-caveat-vectors.mjs  # regenerate the caveat corpus from the real compileCaveats
forge test                     # replay it, plus everything else
```

If `policy.ts` changes, regenerate and the Solidity goes red. That is the point.

The harness was checked by mutation. Each of these four edits turns the suite red, in the
boundary row **and** in several fuzz rows:

| mutation | caught by |
|---|---|
| `amount > cap` → `amount >= cap` | `per_action_cap: amount EQUALS cap (allowed)` |
| empty allowlist → "no restriction" | `contract_allowlist: EMPTY list denies everything` |
| `timestamp >= expiry` → `timestamp > expiry` | `expiry: exactly AT the deadline (denied)` |
| `spent + amount > cap` → `spent > cap` | `session_total_cap: spent + amount is cap+1 (denied)` |

An earlier version of the test base recorded failures in a `failed()` flag the way old DSTest
did. Modern Foundry does not read it, so every assertion silently passed and all four mutations
went green. Mutation checks help prevent an ineffective test harness from
presenting unreliable permission checks as tested protection. The table records
which changed boundaries the tests actually detect.

## What IS enforced on chain

| `Constraint.kind` | enforcer | terms | denial |
|---|---|---|---|
| `contract_allowlist` | `AllowedTargetsEnforcer` | packed 20-byte addresses | `contract_allowlist` / "Target is not allowlisted." |
| `selector_allowlist` | `AllowedSelectorsEnforcer` | packed `bytes4` | `selector_allowlist` / "Function selector is not allowlisted." |
| `asset_scope` | `AssetScopeEnforcer` | `(address[] scope, AmountSite[] sites)` | `asset_scope` / "Asset is outside mandate scope." |
| `per_action_cap` | `PerActionCapEnforcer` | `(address asset, uint256 cap, AmountSite[] sites)` | `per_action_cap` / "Action exceeds per-action cap." |
| `session_total_cap` | `SessionTotalCapEnforcer` | same, **stateful** | `session_total_cap` / "Action exceeds lifetime session cap." |
| `expiry` | `ExpiryEnforcer` | `uint256` unix seconds | `expiry` / "Authorization has expired." |
| `condition` | none in this suite | not applicable | not applicable |

Every denial reverts with `PolicyDenied(string rule, string reason)` carrying the strings
`evaluatePolicy` returns verbatim, so a denial ABI-decodes into the same `{rule, reason}` pair
the API already emits as a `policy` job event. The deny path reads identically whether AiKi or
BNB Chain produced it.

The boundaries are copied, not approximated:

- `expiry` denies at `block.timestamp >= expiresAt`. Equality **denies**.
- `per_action_cap` denies at `amount > cap`. Equality **allows**.
- `session_total_cap` denies at `spent + amount > cap`, checked **before** the execution.
  Equality **allows**.
- **An empty allowlist denies everything.** `evaluatePolicy` produces `values = []` for a
  non-array or empty value, and `[].includes(x)` is always false. The reflexive Solidity
  shortcut `if (terms.length == 0) return; // no restriction` inverts deny-all into allow-all.

`test/Invariants.t.sol` states these four as properties over the full `uint256` domain rather
than as table rows.

### What the API enforces that the chain cannot

- **An unreadable action timestamp** (`expiry` / "Action timestamp is not a valid time."). The
  off-chain `Action.at` is a string that can be malformed; `block.timestamp` is a `uint256` and
  cannot. The API therefore fails closed on a timestamp it cannot parse, and the chain has no
  equivalent case to mirror. This rule has no parity vector for that reason, not by oversight.

  It was a live bug: `Date.parse(action.at) >= Date.parse(policy.expiresAt)` compares `NaN`
  when `at` is garbage, `NaN >= x` is `false`, and an expired mandate accepted the action.

### What the chain enforces that the API does not

The off-chain `Action` type is `{target, selector, asset, amount, at}`. It has no field for
several things a real execution can do, and **the absence of a field is a hole, not a
permission**. The manager therefore refuses, unconditionally and with a distinct error each:

- **native BNB value** (`NativeValueNotSupported`). A redemption carrying `value: 100 ether` is
  scored by `evaluatePolicy` as amount 0 and allowed by every cap. There is no constraint kind
  that can express an authorized native spend, so v1 refuses it outright.
- **batch mode** (`UnsupportedMode`). One `Action` is one call. A batch of N sub-calls each at
  the per-action cap is a redemption the mirror scored as a single action.
- **DELEGATECALL and TRY** (`UnsupportedMode`). Delegatecall runs the target in the account's
  own storage context and voids every caveat; TRY leaves a reverting inner call inside a
  successful transaction, so a balance-delta afterHook measures nothing. Checked in the manager
  **and** independently in the account, because one bug here ends the product.
- **redelegation** (`RedelegationUnsupported`). A sub-delegation's effective policy is the
  intersection of two constraint sets, which `CompiledPolicy` cannot express, and a leaf
  delegation is the cleanest route an agent has to a fresh session counter.
- **non-empty caveat `args`** (`ArgsNotEmpty`). `terms` are signed; `args` are supplied by the
  redeemer at redemption time. Any enforcer that reads them is trusting the attacker to describe
  their own limits.
- **duplicate enforcer addresses** (`DuplicateEnforcer`). `evaluatePolicy` shares one `spent`
  counter across duplicate constraints of the same kind; two identical stateful caveats would
  increment it twice.
- **a missing expiry caveat** (`MissingExpiryCaveat`). A delegation is intentionally reusable -
  that is what a session is - so there is no nonce and the only bounds on reuse are expiry, the
  session cap, and revocation. `compilePolicy` treats expiry as optional; the chain does not. An
  intentionally unbounded mandate has to sign a far-future expiry explicitly rather than omit
  one.
- **self-targeting** (`ForbiddenTarget`). `target` may never be the delegator, the manager, an
  enforcer, or `address(0)`. Calling the account itself would let the agent invoke
  `transferOwnership` on the very account the caveats protect.
- **1-to-3 byte calldata** (`ShortCallData`), which right-pads into a valid-looking `bytes4` and
  reaches the target's fallback.

Refusing to enforce what cannot be mirrored is the correct direction to diverge.

## Known gaps, from this suite's own adversarial review

A 32-agent review of these contracts confirmed ten defects. The critical one is fixed and
tested (`test/Overspend.t.sol`: the stateful enforcer's balance-delta reconciliation had no
test at all, so it could have been deleted wholesale and the suite would have stayed green).
The rest are recorded here rather than quietly carried, because an audit finding nobody wrote
down is an audit that did not happen.

**Specified rather than fixed:** the balance-delta `afterHook` charges any outflow of the asset
during the execution, including one the execution did not name, so the on-chain counter can run
ahead of the off-chain mirror's. That is deliberate and the mirror is the optimistic one: it
knows only the amount in calldata, and trusting that number is exactly the bypass a
fee-on-transfer or rebasing token walks through. The chain is the authority on what actually
moved.

The scope is narrower than it sounds. The snapshot spans one execution inside one transaction,
the manager is non-reentrant, and the account accepts calls only from the manager, so nothing
unrelated can move the delegator's balance in between. What remains is a target the mandate
itself allowlisted drawing on an allowance the delegator granted, which is an outflow the user
authorised twice over. `test/UnnamedOutflow.t.sol` pins the boundary: the extra outflow is
charged to the cap, and one that carries the total past the cap unwinds the whole redemption
rather than reporting it after the money left.

**Also fixed:** two constraints of the same kind were applied in turn off chain, quietly
meaning their intersection, while the chain refused the delegation outright with
`DuplicateEnforcer`. The API therefore accepted mandates whose every action would then fail.
`compilePolicy` now rejects duplicate kinds with the same strictness the chain does, so the two
refuse the same mandate for the same reason.

**Fixed since the review:** `dryRun`'s ALLOW verdict was forgeable by any contract reached
during a `beforeHook`. The enforcers call `balanceOf` on the asset, the asset is just an address
in the signed terms, and a hostile token reverting with the four bytes of `DryRunAllowed` made
the outer catch report that the hooks had completed. The hooks now run one frame deeper, so
anything they revert with is caught and re-wrapped as a denial and the success sentinel is only
reachable after the inner call returned. `test/DryRunForgery.t.sol` reproduces the forgery,
proves a genuine allow and a genuine denial still report correctly, and goes red if the inline
form is restored.

**Test coverage: closed.** All six are now covered by `test/AuditGaps.t.sol`, and each was
mutation-checked by deleting the guard it claims to test:

| guard | deleting it fails |
|---|---|
| `disableDelegationWithSig`'s signature check | 2 tests |
| the enforcer-level snapshot lock | 2 tests |
| `CapTermsLib`'s fail-closed undecodable amount | 2 tests |
| the session cap, reached and stopped at its limit | covered |
| `redeemDelegations` with several executions per call | covered |
| `afterHook` with no snapshot | covered |

The undecodable-amount case is worth recording. The obvious test refuses, but from the
asset-scope enforcer, which sits earlier in the caveat list and cannot decode the call either,
so `CapTermsLib`'s own branch stayed unexecuted and mutating it left the suite green. A second
test uses a mandate with no asset-scope caveat so the cap itself is asked to read the amount.
A test that passes for the wrong reason is the failure mode this table exists to prevent.

All ten findings from the review are now closed: six coverage gaps tested and mutation-checked,
two semantics bugs fixed, and one behaviour specified with its boundary pinned by tests.

That is not a mainnet-readiness claim. These contracts are still **unaudited**, and an
adversarial review by the people who wrote them is worth less than one by people who did not.
The findings above are the ones we thought to look for.

## What is NOT enforced on chain

**`condition` has no enforcer in this suite.** Triggers such as a price threshold
or an approved invoice need their own off-chain implementation; a condition
label alone does not make the policy engine evaluate that business rule. The compiler must show that
line without an on-chain enforcer rather than treating the whole mandate as T0.
`test_NoEnforcerExistsForTheConditionKind` asserts the registry has no entry for it.

**This suite ships lifetime caps, not rolling windows.** `Constraint` has no
period field and `evaluatePolicy` has no periodic reset. The curated web profile
now describes its monthly-cap line as application-side, not T0, but that label
does not add a renewing counter to the policy engine. Do not describe a lifetime
cap as refilling monthly. A periodic cap needs its own implemented accounting
and enforcement contract.

**Revocation is not instant in the world, only in the write.** `disableDelegation` takes effect
at transaction inclusion. Between a revoke click and inclusion, a redemption already in the BNB
Chain public mempool still lands, and the agent can watch for the revocation and front-run it.
The per-action exposure remains bounded by
`min(per_action_cap, session_total_cap - spent)`. Multiple actions before
revocation confirms can consume more than one per-action allowance, up to the
remaining lifetime cap. Do not present the per-action bound as the maximum total
exposure during the pending revocation window
(`test_Documented_ExposureWindowIsBoundedNotEliminated`).

**A target allowlist checks the OUTER call only** - in both evaluators. Allowlisting a router, a
Multicall3, a Permit2 or any forwarding proxy makes the allowlist decorative. This is not a
divergence between the two evaluators; it is a divergence between both of them and the sentence
the UI prints. What still holds in that case is the value bound, because a forwarding selector
has no signed amount site and the cap enforcer denies rather than pricing it at zero
(`test_Attack_ForwarderEscapesTheSelectorAllowlistButNotTheCap`).

**Signature-based value movement is invisible to every caveat.** EIP-2612 `permit` and EIP-3009
`transferWithAuthorization` move value on a signature, not a call, so no enforcer ever runs. The
owner must not sign one for a token a mandate governs, and the agent key must never be the
account owner. That is key management, not something a caveat can enforce.

**Proxy implementation pinning is not here, and the reason matters.** A caveat cannot read
another contract's EIP-1967 storage slot - there is no `extsload` on the EVM - and
`extcodehash(target)` does not change when a proxy is upgraded. So an allowlisted "Venus
Comptroller" can become arbitrary code without the allowlist noticing, and no enforcer in this
suite can detect it. A draft `PinnedImplementationEnforcer` was written and deleted rather than
shipped, because it would have been a contract whose documentation claimed a check it could not
perform. Pinning belongs in the API's pre-flight (`eth_getStorageAt`) and in curation.

## How the amount problem is solved

`evaluatePolicy` receives `Action.amount` and `Action.asset` as fields somebody asserts. The
chain sees only `(target, value, callData)`. Neither can be inferred safely:

- the argument index varies by selector - `transfer` → word 1, `transferFrom` → word 2,
  `approve` → word 1, Venus `repayBorrow` → word 0. A single global "word 1" rule reads address
  high-bits or a deadline for every other shape, yielding a small number that passes the cap;
- the asset frequently is not in the calldata at all. `repayBorrow` moves USDT through an
  internal `transferFrom`; nothing in the top-level call names the token.

So the derivation is **declared in the signed terms**, as an `AmountSite`:

```solidity
struct AmountSite { address target; bytes4 selector; address asset; uint8 argIndex; }
```

Both cap enforcers and the asset-scope enforcer resolve through the same `AmountLib.resolve`, so
they cannot diverge from each other before they diverge from the API. **An execution that
matches no site is DENIED** (`per_action_cap` / "Amount is not decodable for this call."). "Skip
the cap on an unknown selector" and "assume amount zero" are both total bypasses, and this is
the single most important default in the design.

Two independent measurements run, and the **stricter wins**:

1. **Declared** - the word the signed site names, checked in `beforeHook` before anything moves.
   This is what `evaluatePolicy` means by "the amount named in the action", so it is the parity
   surface.
2. **Realised** - the `balanceOf(delegator)` delta across the execution, floored at zero,
   checked in `afterHook`. Decode-free, so it survives proxies, wrappers and unanticipated ABIs.

The charge is `max(declared, realised)`. Delta alone is the **lenient** direction: a call that
pulls 100 and refunds 40 nets 60 while the off-chain action asserted 100, and an inbound
donation mid-transaction masks the outflow entirely. So it is a backstop, never the sole check
(`test_Attack_MovingMoreThanDeclaredIsCaughtByTheDeltaBackstop`).

This also handles the approval attack. `approve(attacker, type(uint256).max)` moves zero tokens
now and everything later, so a delta-only cap reads zero and waves it through. Because the
amount comes from the signed site, an approval is charged at its **full granted value at grant
time**, which is the correct bound (`test_Attack_UnlimitedApprovalIsChargedAtGrantTime`).

## Known divergences from `evaluatePolicy`

These are real and they are listed here rather than absorbed by the tier label.

1. **`asset_scope` compares symbols off chain and addresses on chain.** `Money.asset` is
   `'U' | 'USDT' | 'BNB'` with `assetAddress` merely optional, and `policy.test.ts` uses
   `asset: 'u'`. `evaluatePolicy` lowercases and string-matches. A contract can only match a
   20-byte address, and symbol→address is an off-chain trusted table - exactly the ambiguity a
   fake-token scam exploits. **An `asset_scope` expressed in symbols is T1 at best, whatever
   enforcer is attached.** The corpus uses addresses on both sides so the two are comparing the
   same predicate; the compiler must normalise to addresses or the T0 label on that line is
   false.
2. **`session_total_cap` sums across assets off chain and cannot on chain.** `evaluatePolicy`
   adds `action.amount` to one scalar regardless of `action.asset`, so a mandate scoped to
   {USDT, BNB} adds 18-decimal USDT units to wei as if they were one quantity. There is no
   faithful on-chain mirror of that, and the single-scalar behaviour is itself wrong. This
   enforcer is per-token: a call moving any other asset is denied
   ("Call moves an asset this cap does not price."). A multi-asset cap needs a price oracle,
   which imports oracle manipulation - do not build one, downgrade the tier.
3. **`spent` means different things.** Off chain it is what the API relayed, charged at attempt
   time even when the transaction later reverted; on chain it is what actually moved. The API's
   counter drifts monotonically upward and starts denying actions the chain would still permit -
   and the agent holds a valid delegation and can redeem without touching AiKi's relay at all.
   **Read `SessionTotalCapEnforcer.spentOf(manager, delegationHash)`.** Two counters that
   disagree is worse than one that is occasionally stale.
4. **The session is the delegation.** Two delegations compiled from one policy get two
   independent budgets, i.e. twice the cap. Mint exactly one delegation per session
   (`test_SessionCap_SpentIsIsolatedPerDelegation`).
5. **Re-authorization silently resets the budget**, and re-signing with the *same* salt silently
   resumes the old one - a user renewing an exhausted $250 mandate gets one with zero remaining
   and no error anywhere. Both are invisible unless the UI says so
   (`test_Documented_ReAuthorizationResetsTheSessionBudget`).
6. **Expiry resolution.** `Date.parse` is milliseconds, `block.timestamp` is seconds, and BNB
   Chain validators have discretion over the timestamp at ~0.75s blocks. The two agree except
   within a few seconds of the deadline. That window is irreducible. Compile whole-second
   expiries and treat the boundary as indeterminate rather than as a divergence.
7. **Duplicate kinds are rejected during API compilation and duplicate enforcers are rejected on chain.** Keep both checks; allowing duplicates in only one layer produces a mandate the other cannot execute (`test_RejectsDuplicateEnforcers`).
8. **A malformed `terms` blob denies with rule `structure`, not with the constraint's rule.** It
   is still a denial; only the reported reason differs.

### Current API checks and remaining integration risks

`compilePolicy` rejects duplicate constraint kinds, non-string expiry values
and unparseable expiry strings. `evaluatePolicy` fails closed on an unreadable
action timestamp. These are implemented checks, not outstanding expiry bugs.

The public authorization route calls `describeEnforcement` and
`withDerivedTiers` before storing a policy. The lower-level `compilePolicy`
function still reduces the tiers it receives, so internal callers must preserve
that derivation rather than supply their own trust labels.

Cap evaluation still uses `BigInt(String(c.value))`; malformed decimal or
exponent values can throw. Input validation and route error handling remain
necessary. A compiler outcome marked application-side is not proof that every
business rule has an implemented runtime check.

## Compiler integration requirements

These requirements apply to a chain-enforcement claim. The runtime can retain
an unsigned authorization with application-side outcomes when compilation is
unsupported, but it must not present a missing caveat as T0. A signed delegation
must preserve the supported limits the owner reviewed.

- **Derive `tier` from caveat compilation against the configured deployment.** The public authorization route already does this through `withDerivedTiers`; preserve that boundary for new callers.
- **Emit one caveat per constraint INSTANCE, in `policy.constraints` order, with `expiry`
  hoisted to index 0.** Never merge same-kind allowlists for gas: the off-chain loop ANDs every
  constraint, so two `contract_allowlist`s intersect, and merging turns that into a union.
- **Reject, do not coerce**: non-address allowlist entries (`'0xvenus'` is accepted today);
  selectors that are not exactly `0x` + 8 lowercase hex (`'0x1'` is used in the existing test);
  symbol-valued `asset_scope`; negative or non-integer caps (`BigInt('-1')` denies everything
  off chain and becomes `type(uint256).max` under a naive cast, an exact inversion);
  sub-second, numeric, or duplicated expiry values; allowlists longer than 32 entries; and any
  unknown constraint kind, via an exhaustive switch that throws.
- **Take enforcer addresses only from `AiKiEnforcerRegistry`,** and have the UI resolve every
  caveat's enforcer through it. A user socially engineered into signing a delegation whose
  "AllowedTargetsEnforcer" is a lookalike that returns without checking anything holds a mandate
  that renders as T0 and enforces nothing. The manager will run a lookalike happily - the
  registry is a check the compiler and the UI must perform, not one the chain performs
  (`test_RegistryIdentifiesGenuineEnforcersOnly`).
- **Mint a fresh 256-bit salt per authorization** and store it beside `authorizationId`.
- **Call `dryRun` on every attempt** and alarm on any mismatch with `evaluatePolicy`. That turns
  "the API's answer is the chain's answer" from a design intention into a monitored runtime
  invariant, and it is the highest-value integration in this whole build.
- **Verify the account's authority graph before writing `verified: true`.** T0 is a property of
  the delegator ACCOUNT, not of the caveat set. If the agent's key is also an owner or a second
  executor, the caveats are decoration.

## Layout

```
src/core/        Types, Errors, ExecutionLib, EncoderLib (EIP-712), SignatureLib,
                 AmountLib, CapTermsLib, the two enforcer bases, AiKiDelegationManager
src/enforcers/   one per enforceable constraint kind
src/account/     AiKiMandateAccount -- the delegator, with an auditable authority graph
src/registry/    AiKiEnforcerRegistry -- what `enforcedBy` resolves against
src/interfaces/  ICaveatEnforcer, IDelegationManager, IDeleGatorCore, IERC20, IERC1271
test/            Parity (the corpus), Enforcers, Manager, Attacks, Invariants
tools/           gen-vectors.mjs -- imports the real evaluatePolicy
script/          Deploy.s.sol -- deployment entry point; review the explicit target network
```

**Zero external dependencies.** No `lib/`, no forge-std, no OpenZeppelin. Every interface,
including the Foundry cheatcode interface and the assertion base in `test/base/`, is written by
hand. Nothing here depends on a network install succeeding.

`solc 0.8.28` pinned, `evm_version = "shanghai"` - deliberately **not** Cancun, so nothing
depends on EIP-1153 transient storage, whose availability on chain 56 is not verified in this
repository. The reentrancy guard uses a plain storage slot. `via_ir` is required, not optional:
the seven-parameter ERC-7710 hook signature alone exhausts the legacy codegen stack.

## Security properties, and what they rest on

The manager and every enforcer are **non-upgradeable, ownerless, non-pausable**, with no
`delegatecall` and no `selfdestruct`. Migration is a fresh deployment plus fresh signatures.
Any upgradeability anywhere in this set silently converts the whole system from T0 to T1 -
"the chain enforces it" would actually mean "a proxy admin enforces it".

The EIP-712 preimage covers the **full** caveat array, every enforcer address and every terms
blob, and excludes the signature. Both halves matter: an agent that drops a cap enforcer
produces a different hash and an invalid signature
(`test_DroppingACaveatInvalidatesTheSignature`), and hashing the signature would mean a
flipped-`s` copy produced a new `delegationHash` for the same semantic delegation, and therefore
a fresh session counter and unbounded spend.

Signatures: strict ECDSA (EIP-2 low-`s`, canonical `v`, non-zero recovery) for a bare EOA;
ERC-1271 with **no** ECDSA fallback for a genuine contract account, because a fallback would
defeat account-level key rotation; and for an EIP-7702 delegated EOA - 23 bytes of code prefixed
`0xef0100`, live on BNB Chain since Pascal - ERC-1271 first and ECDSA as a fallback, which is
sound there and only there because the EOA key can re-delegate at will. The ERC-1271 call is a
bounded staticcall that copies at most 32 bytes and requires exactly 32 back, so a hostile
account cannot return-bomb the manager.

Stateful enforcer state is protected twice: `onlyManager` against an immutable address, **and**
keyed by `msg.sender` so even a second manager cannot reach these counters. Every hook is a
public function; without the pin, anyone could call `beforeHook` with a victim's
`delegationHash` and brick a live mandate (`test_Attack_OutsiderCannotPoisonASessionCounter`).

Revocation is **one-way**. There is no `enableDelegation`: a re-enable path is a re-entry point
for any agent that can induce a call into the manager. `disableDelegationWithSig` lets a user
holding no BNB revoke through a relayer - that user is precisely the one whose agent has gone
wrong. `bumpEpoch()` kills every outstanding mandate of a delegator in one transaction, because
`epoch` sits inside the signed struct.

**This suite has not had an independent security audit.** Address and bytecode
checks establish which deployment the API uses, not that its contracts are safe.
Any `verified: true` presentation must say what was verified and preserve the
unaudited testnet qualification.
