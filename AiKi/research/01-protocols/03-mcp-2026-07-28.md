# Model Context Protocol — Spec `2026-07-28`

**Research verdict:** SOLID
**Source:** shallow clone of `modelcontextprotocol/modelcontextprotocol` @ commit `4df2d6b` (2026-08-14)
**Answers:** Charter question **A5**

---

## Headline

**`2026-07-28` is the largest breaking revision MCP has had.** If AiKi's MCP surface were designed from memory of the 2025 spec, essentially every architectural assumption would be wrong.

| Removed / changed | Was |
|---|---|
| `initialize` + `notifications/initialized` | The handshake |
| `Mcp-Session-Id` | Session affinity |
| SSE resumability (`Last-Event-ID`) | Stream recovery |
| **Server-initiated requests** | How elicitation and sampling worked |
| `ping`, `logging/setLevel` | Core methods |
| **Tasks** | Core (experimental) → **moved to a draft extension** |
| Roots, Sampling, Logging | Core features → **deprecated** |

Version history — the strings *are* the dates: `2024-11-05` → `2025-03-26` → `2025-06-18` → `2025-11-25` → **`2026-07-28`**.

```ts
export const LATEST_PROTOCOL_VERSION = "2026-07-28";   // schema/2026-07-28/schema.ts:30
```

`schema/draft/schema.ts` carries the same value — draft has not advanced past the release.

## 1. The protocol is now stateless

Sessions are gone at the protocol level (SEP-2567). List endpoints no longer vary per connection. Servers needing cross-call state use, verbatim:

> "explicit, server-minted handles passed as ordinary tool arguments."

The handshake is replaced by `server/discover` (**MUST**-implement):

```ts
DiscoverResult extends CacheableResult {
  supportedVersions: string[];
  capabilities: ServerCapabilities;
  instructions?: string;   // guidance for the model; MUST NOT duplicate tool descriptions
}
```

Every request carries:
```
_meta["io.modelcontextprotocol/protocolVersion"]
_meta["io.modelcontextprotocol/clientCapabilities"]
```

**→ This suits AiKi well.** A stateless protocol maps cleanly onto the MPSS's "UI, API, MCP and SDKs are sibling surfaces over the same canonical backend." No session store, no sticky routing for ordinary calls, and `job_id` / `authorization_id` are already the server-minted handles the spec asks for.

### Required transport headers

Streamable HTTP now demands routing headers on every POST:

| Header | Value |
|---|---|
| `MCP-Protocol-Version` | e.g. `2026-07-28` — **MUST** match `_meta` protocolVersion, else `400` + `HEADER_MISMATCH (-32020)` |
| `Mcp-Method` | the JSON-RPC method |
| `Mcp-Name` | for `tools/call`, `resources/read`, `prompts/get` — the tool/resource name |

Client `Accept` **MUST** list both `application/json` and `text/event-stream`.

**→ These exist so intermediaries can route without parsing the body.** AiKi's gateway can rate-limit, authorize and shard on headers alone — genuinely useful for a marketplace whose tools have wildly different cost profiles (`search_agents` vs `create_job`).

Transports: **stdio** and **Streamable HTTP** only. HTTP+SSE (2024-11-05) is formally deprecated. `subscriptions/listen` — a long-lived POST-response SSE stream — replaces the GET endpoint and `resources/subscribe`.

## 2. Long-running work: Tasks exist, but as a draft extension

This was the make-or-break question. AiKi's jobs run **minutes to days**; a request/response tool call cannot carry that.

**Answer: MCP can carry it — via `io.modelcontextprotocol/tasks`, which is an official extension whose spec repo is still marked `draft` and "under development."**

```ts
export type TaskStatus =
  | "working"          // being processed
  | "input_required"   // waiting for elicitation/sampling input
  | "completed"        // terminal
  | "failed"           // terminal
  | "cancelled";       // terminal

export interface Task {
  taskId: string;
  status: TaskStatus;
  statusMessage?: string;
  createdAt: string;      // ISO 8601
  lastUpdatedAt: string;  // ISO 8601
  ttlMs: number | null;   // null = unlimited; server may discard after TTL
  pollIntervalMs?: number;
}
```

```ts
tasks/get     { taskId }              → Result & DetailedTask   // resultType MUST be "complete"
tasks/update  { taskId, inputResponses }  → Result              // empty ack
tasks/cancel  { taskId }              → Result                  // cooperative, eventually consistent
notifications/tasks/status            → DetailedTask
```

A server responds to a supported request with `CreateTaskResult` (`resultType: "task"`), and **MUST NOT** do so for a client that did not declare the extension capability on that request (`-32003` / `-32021`).

**Transport routing:** verbatim from the extension spec —

> "When `tasks/get`, `tasks/update`, or `tasks/cancel` is sent over the Streamable HTTP transport, the client MUST set the `Mcp-Name` header to the value of `params.taskId`. This allows transport intermediaries and load balancers to route subsequent requests for the same task to the server instance holding its state."

**→ Assessment.** The shape is complete and buildable, and it is a genuinely good fit: poll-first with optional notifications, cooperative cancellation, mutable TTL, and an `input_required` state that maps exactly onto AiKi's human-approval gate. The five statuses project cleanly onto the canonical job state machine.

**→ But it is a pre-release extension.** Building AiKi's machine surface on it is a bet. The mitigation is the one the MPSS already mandates: the canonical job lifecycle is AiKi's own, and MCP Tasks is one *projection* of it. If the extension churns, an adapter changes; the job model does not. **This belongs in ADR-010 (MCP/API versioning) as an explicit, dated risk.**

## 3. ⚠️ Elicitation is now a retry loop, not a callback

This is the change with the sharpest consequence for AiKi, because **spend approval is an elicitation**.

Verbatim:

> "Servers MUST send server-to-client requests (such as `roots/list`, `sampling/createMessage`, or `elicitation/create`) using the MRTR pattern. The previous pattern of server-initiated requests is no longer supported. **This is a breaking change.**"

**MRTR** (Multi-Round Tool Response) works like this:

1. Server returns `InputRequiredResult`:
   ```ts
   { resultType: "input_required",
     inputRequests?: { [key]: ElicitRequest | CreateMessageRequest | ListRootsRequest },
     requestState?: string }   // opaque
   ```
   Server MUST include at least one of the two, and MUST NOT send an `inputRequest` type the client did not declare.
2. **The client re-issues the ORIGINAL request with a NEW JSON-RPC id**, carrying `inputResponses` + the echoed `requestState`.

The elicitation *schema* is unchanged in substance (`form` and `url` modes; `ElicitRequestFormParams` with `message` + `requestedSchema`). Only delivery changed.

### 🔒 A security requirement AiKi must not miss

> `requestState` is an **attacker-controlled opaque blob**. Servers **MUST** integrity-protect it and **SHOULD** bind principal, TTL, and originating request.

For AiKi this is not boilerplate. `requestState` will carry the pending job and its authorization context. An unbound, unauthenticated `requestState` is a **direct privilege-escalation and replay vector on spend approval** — a client could replay an approval, or swap in state minted for a different principal.

**Requirement:** `requestState` MUST be a MAC'd or encrypted envelope binding `{principal, job_id, authorization_id, nonce, expiry}`, verified before any economically meaningful action. This lands squarely in the MPSS's existing threat model under payment replay and permission escalation.

**→ Product consequence:** approval-over-MCP works, but as poll-and-resubmit rather than push. For a human-in-the-loop spend approval that may take minutes, **the Tasks `input_required` status is the better carrier than a bare MRTR round-trip** — it is designed for exactly this and survives disconnection.

## 4. Authorization

| Requirement | Level |
|---|---|
| OAuth 2.1 (`draft-ietf-oauth-v2-1-13`) | Server = resource server; client = OAuth client |
| **RFC 9728** Protected Resource Metadata | **MUST** for servers; clients MUST use it for AS discovery |
| **RFC 8707** Resource Indicators | **MUST** for clients |
| RFC 9207 `iss` | SHOULD emit / **MUST** validate |
| **RFC 7591 Dynamic Client Registration** | **DEPRECATED** |

401 carries `WWW-Authenticate: Bearer resource_metadata=…`.

**Client registration priority:**
1. Pre-registered / out-of-band `client_id`
2. **Client ID Metadata Documents (CIMD)** — URL-as-`client_id`, if the AS advertises `client_id_metadata_document_supported: true`
3. DCR (backwards compatibility only; now requires `application_type`)

CIMD: the client hosts metadata at an HTTPS URL; the `client_id` URL **MUST** use `https` **and** contain a path component.

**→ AiKi's MCP server is an OAuth 2.1 resource server with mandatory RFC 9728 + RFC 8707.** Resource indicators matter here specifically: they stop a token minted for one resource being replayed against another — which is exactly the protection a marketplace holding spend authority needs. This is more prescriptive than the 2025 spec and should be treated as a hard requirement, not a nice-to-have.

## 5. Other changes that affect design

### Tools
```ts
Tool extends BaseMetadata, Icons {
  description?: string;
  inputSchema:  { $schema?: string; type: "object"; [k: string]: unknown };
  outputSchema?: { $schema?: string; [k: string]: unknown };
  annotations?: ToolAnnotations;
  _meta?: ...;
}
```
Both schemas now accept **any JSON Schema 2020-12 keyword** — `oneOf`/`anyOf`/`allOf`/`not`, `if`/`then`/`else`, `$ref`/`$defs`. `structuredContent` is now **any JSON value**, not just an object.

**→ Directly useful.** AiKi's work-order and policy objects are genuinely polymorphic (payment models, policy dimensions, category-specific metrics). Full 2020-12 means the MCP tool surface can express the real schema instead of a flattened approximation — which serves `FR-M2M-002` ("MCP/API calls must return typed evidence, not only prose").

### Caching is now mandatory on list/read
```ts
CacheableResult extends Result {
  ttlMs: number;        // required. 0 = immediately stale
  cacheScope: ...;      // required
}
```
**→ AiKi must set these deliberately.** A Passport is a projection over live evidence; a stale-cached Passport is a wrong hiring decision. Liveness-sensitive results need low `ttlMs`; static manifests can be long. This is the freshness discipline the MPSS asks for, now enforced by the protocol.

### Deprecated with a ≥12-month removal window (SEP-2577)
**Roots, Sampling, Logging.** Suggested migrations: pass directories/files as tool parameters or resource URIs instead of Roots; **integrate directly with LLM provider APIs instead of Sampling.**

**→ Do not build on Sampling.** AiKi's Model Gateway calls providers directly anyway, which is now also the official guidance.

### Error model
```
PARSE_ERROR      -32700    HEADER_MISMATCH                    -32020
INVALID_REQUEST  -32600    MISSING_REQUIRED_CLIENT_CAPABILITY -32021
METHOD_NOT_FOUND -32601    UNSUPPORTED_PROTOCOL_VERSION       -32022
INVALID_PARAMS   -32602
INTERNAL_ERROR   -32603
```
`-32000..-32019` remains implementation-defined (grandfathered).

### Pagination
Unchanged: opaque `cursor`, no numbered pages, server-determined page size, clients MUST NOT assume a fixed size.

### Observability
OpenTelemetry trace context via `_meta` keys `traceparent`, `tracestate`, `baggage` (SEP-414).

**→ Adopt immediately.** The MPSS requires correlation IDs spanning gateway → policy → payment → agent → evaluator. This makes an MCP client's trace continue into AiKi's internal spans for free.

⚠️ `_meta` prefix rule: any prefix whose second label is `modelcontextprotocol` or `mcp` is **reserved** — `io.modelcontextprotocol/`, `dev.mcp/`, `org.modelcontextprotocol.api/`, `com.mcp.tools/` are all reserved. AiKi must namespace its own `_meta` keys accordingly (e.g. `ai.aiki/…`).

### ⚠️ Rate limiting is essentially unspecified
A grep across the entire `2026-07-28` spec returns three soft SHOULDs and **no `429` semantics, no `Retry-After`**.

**→ AiKi must define its own and document it.** For a marketplace where a single tool call can trigger a paid job, unspecified rate limiting is a real exposure. Use the required routing headers (§1) to price and limit per method and per tool without parsing bodies.

## 6. Impact on AiKi

| Finding | Consequence |
|---|---|
| **`2026-07-28` is heavily breaking** | Any MCP design from 2025 memory is wrong. Pin to this revision; version the adapter. |
| Protocol is stateless | Fits the sibling-surfaces architecture. `job_id` is the server-minted handle the spec wants. |
| Routing headers required | Gateway can authorize, price and shard without body parsing. |
| **Tasks moved to a draft extension** | MCP *can* carry the job lifecycle; it is a bet on pre-release. Canonical job model stays AiKi's; MCP is a projection. **ADR-010.** |
| Task statuses map to AiKi's lifecycle | `input_required` is the natural carrier for human spend approval. |
| **Server-initiated requests removed** | Approval is poll-and-resubmit (MRTR), not push. Prefer Tasks for long approvals. |
| **`requestState` is attacker-controlled** | **MUST** be integrity-protected and bound to `{principal, job_id, authorization_id, nonce, expiry}`. Replay/escalation vector on spend approval. |
| OAuth 2.1 + RFC 9728 + RFC 8707 mandatory | Hard requirement. Resource indicators prevent cross-resource token replay. |
| DCR deprecated → CIMD | Client onboarding design changes. |
| Full JSON Schema 2020-12 | Express real work-order/policy schemas, not flattened ones. |
| `ttlMs` + `cacheScope` required | Freshness becomes explicit. Passport TTL must be short. |
| Sampling deprecated | Model Gateway calls providers directly — now also official guidance. |
| OTel `_meta` conventions | Free trace continuity from client into AiKi. Namespace own keys as `ai.aiki/…`. |
| **Rate limiting unspecified** | AiKi must define and document its own. |
